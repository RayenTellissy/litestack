## Bill split fix

Splitting a bill now always prints a Total equal to the amount entered. Anyone who splits an amount that doesn't divide evenly gets every cent back. So does anyone who types the same name twice. Each share differs from the others by at most one cent. The work is in 4 commits on `fix/split-remainder`. There is no remote, so there is no PR.

**What was broken.** `allocate` in `tabsplit/money.py` used floor division (`total_cents // parts`) and threw away the remainder. 10000 cents over 3 people became `[3333, 3333, 3333]`, which is 1 cent short. I measured this with a probe that printed `parsed 10000 shares [3333, 3333, 3333] sum 9999 lost 1`. Parsing and formatting were correct. While checking the word "always", I found a second loss with its own cause. `split_even` in `tabsplit/bill.py` stored shares in a dict keyed by name, so a repeated name overwrote the earlier share. `100.00 alice alice bob` printed `Total: $66.66`.

**Root cause and fix.**
- `allocate` now uses `divmod`. It gives one extra cent to each of the first `remainder` parts.
- `split_even` now returns an ordered list of (name, share) pairs. Every name you enter keeps its own share.
- `receipt` still adds up the shares to print the Total. The Total line therefore still exposes any shares that don't add up.

**Failing output before the fix:**
```
$ python3 -m tabsplit 100.00 alice bob carol
alice: $33.33
bob: $33.33
carol: $33.33
Total: $99.99
$ python3 -m tabsplit 100.00 alice alice bob
alice: $33.33
bob: $33.33
Total: $66.66
```
**Passing output after the fix:**
```
$ python3 -m tabsplit 100.00 alice bob carol
alice: $33.34
bob: $33.33
carol: $33.33
Total: $100.00
$ python3 -m tabsplit 100.00 alice alice bob
alice: $33.34
alice: $33.33
bob: $33.33
Total: $100.00
```

**How I verified it.**
- Three pin tests were committed as `unittest.expectedFailure` before each fix. Run without the mark, they failed (`'...Total: $99.99' != '...Total: $100.00'`, `[3333, 3333, 3333] != [3334, 3333, 3333]`, `'...Total: $66.66' != '...Total: $100.00'`).
- `python3 -m unittest discover -s tests` now gives `Ran 12 tests ... OK`.
- `.git/litestack/check_totals.py` runs the CLI over 10 cases (amounts, tips, repeated names). It then checks `allocate` for every total from -500 to 5000 cents over 1 to 12 people. At the branch tip it gives `FAILURES: 0`. Against main's package it gives `FAILURES: 48948`. Its output is kept in `.git/litestack/check_totals-after.txt` and `.git/litestack/check_totals-main.txt`.
- `allocate` has one caller, `split_even`, and `split_even` has one caller, `receipt` (checked with grep). Even splits and tips print the same as before (`90.00` → `$90.00`, `80.00 --tip 15` → `$92.00`).

### Review
Verdict: **PASS+NOTES**. The reviewer reran the repro and the pins. It also ran 20,000 random splits through `main()`, plus repeated-name and tip cases, and found 0 mismatches.
- Fixed. Finding 2 (nit) said the kept main-side comparison output came from an older version of the script. I regenerated it with the current script, and it now reads `FAILURES: 48948`.
- Not fixed, listed under Needs your call. Finding 1 (warning) says a negative amount with cents still prints a different Total, for example `-10.50` → `Total: -$9.50`. It also says amounts with more than two decimals are cut off rather than rounded, for example `100.009` → `$100.00`. The cause is in `parse_amount`, which this change does not touch and does not make worse. Main prints the same thing.

### Needs your call
- **Who gets the extra cents.** They go to the first names, in the order you typed them. `100.00 alice bob carol` gives alice `$33.34`.
- **Repeated names.** A repeated name prints one line per entry (`alice: $33.34`, `alice: $33.33`). The alternatives were to merge the entries into one line or reject the input with an error. I kept it as one line per entry because main already accepts repeated names, and this way it adds no new error.
- **Negative and sub-cent amounts.** `parse_amount` still gets negative amounts with cents wrong, and still cuts off digits past two decimals. Both are parsing problems, not splitting problems. The tool's examples only show positive amounts with two decimals. Rejecting these inputs or supporting them is a product choice, so I left them for a separate change.

### Principles that changed a decision
- **Fix root causes.** I fixed the remainder inside `allocate`. The alternative was to print the entered amount as the Total, but that would hide shares that don't add up.
- **Model the domain.** Shares became an ordered list of (name, share) pairs instead of a dict. Names can repeat, so a dict keyed by name was the wrong shape.
- **Smallest change.** I left the `parse_amount` sign and decimal handling alone, and the reviewer agreed.
- **Verifiable units.** The commits go failing test, then fix, for each of the two causes.
- **Prove it works.** I scripted the before-and-after comparison so it reruns the same way.

### Not verified
- The project has no lint or type checker, so nothing ran there. I ran `compileall`, and it passed.
- I tested only on Python 3.9.6, the one interpreter installed here.
