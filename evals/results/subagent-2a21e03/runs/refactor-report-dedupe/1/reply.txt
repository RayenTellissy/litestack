The three summary reports print exactly what they printed before. Their grouping, totals and table layout now live in one place, so a change to the report layout is one edit instead of three. It is committed on a new branch. There is no PR because the repository has no remote.

**What changed in the structure.** `ledger/reports.py` has one private function, `_summary(entries, period_key)`. It holds the grouping, the per-category totals, the grand total, the table formatting and the "No entries." case. The three public functions only supply how a date maps to its period label:
- `daily_summary` uses the ISO date.
- `weekly_summary` uses a small nested `iso_week`.
- `monthly_summary` uses year and month.

Public names and signatures did not change. `parse_line` was not touched. The diff is 11 lines added and 34 removed, in that one file.

**The pin.** Two checks, both run before the first edit and after each of the three moves:
- The existing tests, with `python3 -B -m unittest discover -s tests`. 5 tests passed every time (measured).
- A script that records the output of all three functions on 25 input sets, which is 75 results. It records the exception type and message when a call fails. The inputs include:
  - The test data, an empty list and a generator.
  - ISO week-year edges such as 2024-12-30 and 2027-01-01.
  - Years below 1000.
  - Int, negative, NaN and infinite amounts, and categories wider than the column.
  - Bad inputs, plus a 10,000-entry seeded random set.
  - One case where the grand total depends on the order categories are added. On Python 3.9 it prints 0.00, and 1.00 if summed in sorted order.

I checked that the script would catch a real change. A copy that summed the totals in sorted order produced a different recording (measured).

**Proof the output did not change.** At the branch tip, the recording is byte-identical to the one taken at the base. Both are 817,023 bytes and `cmp` exits 0 (measured). The reviewer reran it and got the same result. It also rebuilt the base code itself and confirmed the saved baseline really comes from it.

**Principles that changed a decision.**
- **Model the domain.** The only thing that differs between the reports is how a date maps to its period label. So the shared function takes a function from date to label, rather than a mode flag or a lookup table.
- **Smallest change.** The shared body is the old body, unchanged. The order of additions and the empty-report check are the same, so the floating-point results cannot drift. The awkward inline import in `parse_line` stays, because it is unrelated to the request.
- **Reader load.** `iso_week` is nested inside `weekly_summary`, its only caller, rather than added as a new module-level function.
- **Prove it works.** I added the order-sensitive total case and checked that the recording catches a change, because the existing tests could not tell a summation-order change apart.
