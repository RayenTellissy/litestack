The three reports now share one implementation, and their output is unchanged. `daily_summary`, `weekly_summary` and `monthly_summary` give the same strings as before. A fix to the grouping, totals or table format now goes in one place instead of three.

**What changed**
- The grouping, per-category totals, table rows, total row and `"No entries."` fallback are now in one private function, `_summary(entries, period_of)`, in `ledger/reports.py`.
- Each public function keeps its name and signature. It passes only its rule for turning a day into a period:
  - daily uses `day.isoformat()`
  - weekly uses the ISO year and week, formatted `YYYY-Www`
  - monthly uses `YYYY-MM`
- The diff is 11 lines added and 35 removed, in one file.

**The pin**
- **Existing tests:** `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests` passed 5 tests before and after the change.
- **Comparison script:** the tests left gaps, so I added `.git/litestack/compare_summaries.py`. It runs the module from `main` and the working tree on the same inputs and makes 49 comparisons. The inputs cover:

  - unsorted input and ISO-week year boundaries

  - the error type and message for bad input

**Principles that changed a decision**
- **Model the domain:** the only thing that differs between the reports is the day-to-period rule. So that rule is the single parameter. I did not split grouping, totals and formatting into separate helpers.
- **Smallest change:** I kept the existing two passes, grouping first and totals second. Merging them would change which error bad input raises first, and the pin checks that error.
- **Smallest change:** daily passes `lambda day: day.isoformat()` rather than `date.isoformat`. The unbound method would drop the time from `datetime` days. The pin has a case for this.
- **Smallest change:** I left `parse_line`'s local `datetime` import alone because it is outside the request.
- **Prove it works:** the comparison against `main` is a script that reruns the same way. Its output is kept, and the mutation run shows it can fail.
- **Design step and Subtract first were skipped:**
  - The design step was not needed. There is no new type or module, and no signature another module calls changes. `_summary` is private.
  - The touched code had nothing dead to remove first.
