**Litestack refactor. Committed locally. No PR, because the repository has no remote.**

Nothing changes for code that calls `daily_summary`, `weekly_summary` or `monthly_summary`. Across 2478 recorded cases the output is byte-for-byte the same as before (measured). The grouping, totals and table layout now live in one place, so a future change to them is one edit instead of three.

**What changed**
- A new private function, `_summary(entries, period_key)` in `ledger/reports.py`, now holds the only copy of the grouping, the per-category totals, the header and table rows, the total row and the "No entries." fallback.
- The three public functions are now one line each and only supply how to label a period:
  - Daily passes `lambda day: day.isoformat()`.
  - Weekly passes a new `_iso_week` helper.
  - Monthly passes the `YYYY-MM` format.
- Function names, signatures and `parse_line` are unchanged. One file changed, with 12 lines added and 34 removed.

**The pin (what had to stay the same)**
- The existing unit tests, `python3 -m unittest discover -s tests`, which have 5 tests.
- A script that saves every summary's output so before and after can be compared: `.git/litestack/record_outputs.py`.
  - It runs all three summaries on 13 fixed inputs and 400 seeded random entry lists. Each list is passed both as a list and as a single-use iterator.
  - The fixed inputs cover dates where the ISO week belongs to a different year (such as `2020-W53` and `2025-W01`), `datetime` values as days, rounding edge cases, the order floats are added in, long and empty category names, years before 1000, and three error cases.
  - I saved the baseline at `e122dd5` before any edit. A second run matched it exactly.
- I checked that the script can catch a wrong refactor by running it against two deliberately broken copies, made outside the working tree:
  - Using `date.isoformat` as the daily key changed 3634 output lines, because `datetime` days would lose their time part.
  - Adding up the total from the entries, instead of from the category subtotals, changed 12 output lines.
  - I did not run the unit tests against these broken copies. From their inputs I infer they would pass both.

**Proof the output did not change**
- The unit tests reported `Ran 5 tests ... OK` after each of the two steps.
- Comparing `.git/litestack/baseline.txt` with `.git/litestack/after.txt` found no differences across 144400 lines. The comparison after the first step, `.git/litestack/step1.txt`, was also identical.

**Is it easier to read?**
- Before, the file was 65 lines and held three 17-line copies. A reader had to compare all three to find the one line that differed.
- After, it is 43 lines with one shared body. Each public function adds one step into `_summary`.
- Overall it is easier to read, so the change stays.

**Principles that changed a decision**
- **Model the domain.** The only difference between the three functions is how they label a period. So the helper takes one labelling function, rather than being split into separate grouping, totals and formatting helpers.
- **Smallest change.** The shared body was moved without rewriting it, so the diff is easy to review. The inline import in `parse_line` stayed, and no tests were added to the repository.
- **Prove it works.** Reading the original code showed that calling `entry.day.isoformat()` on the value itself matters, because a `datetime` day gives a different string. So the daily key stays `lambda day: day.isoformat()` and not the shorter `date.isoformat`. The saved-output comparison covers this and the order floats are added in, and the broken-copy run shows it would catch either mistake.
- **Reader load.** I compared before and after, confirmed the code is easier to read, and kept the change.
