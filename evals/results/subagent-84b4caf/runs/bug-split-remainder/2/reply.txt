## Bill split fix: total now always matches the amount entered (uneven splits)

Splitting a bill that doesn't divide evenly no longer loses cents. `python3 -m tabsplit 100.00 alice bob carol` now prints `Total: $100.00`. Each leftover cent goes to the people listed first, so no two shares differ by more than one cent. The fix is two commits on branch `fix/split-remainder`. There is no PR because the repository has no remote.

**What was broken.** `allocate` in `tabsplit/money.py` gave everyone `total_cents // parts` and threw away the remainder. A three-way split could lose up to 2 cents (up to one cent per person after the first). A probe confirmed `parse_amount('100.00')` is `10000` and `allocate(10000, 3)` is `[3333, 3333, 3333]`, which sums to 9999. So the loss starts in `allocate`. `receipt` only adds up what it is given.

**The fix.** `allocate` now uses `divmod` and adds one cent to each of the first `remainder` shares:
```python
share, remainder = divmod(total_cents, parts)
return [share + 1] * remainder + [share] * (parts - remainder)
```
Its only caller is `split_even` → `receipt`.

**Tests.** The pin commit adds two tests:
- `test_uneven_receipt_totals_the_amount` checks the printed receipt for `$100.00` split three ways.
- `test_shares_sum_to_total` checks that the shares add up to the total and differ by at most one cent, for 10000, 9998, 5 and 1 cents.

Without the expected-failure marks, both failed at the pin commit (`Total: $99.99' != ... Total: $100.00'` and `9999 != 10000 : [3333, 3333, 3333]`). After the fix, `python3 -m unittest discover -s tests -v` runs 11 tests, all OK.

## Review

The independent reviewer's verdict is **PASS+NOTES**. It had no findings, so there was nothing to fix and nothing to dismiss. It reran the tests and the proof script and got the same results. It also tried more splits (`0.02 a b c`, `99.99 a b c d e f`, `0 a b`, `100.00 a b c --tip 15` → `$115.00`), and every total matched. I re-ran its two base-failure cases myself and both behave as it described.

**Needs your call:**
- **Who gets the leftover cents.** The people listed first each pay one cent more. The request doesn't decide this. The last person or the payer would also work. The receipt test now pins the first-listed order.
- **Duplicate names still lose money (fails at base too).** `100.00 alice alice bob` prints only alice and bob and `Total: $66.66`. That's a separate bug: `split_even` keys shares by name in a dict, so a repeated name overwrites its own share. Fixing it means choosing between rejecting duplicate names at the CLI and listing each occurrence as its own line. I left it out of this change.
- **Negative amounts with cents parse wrong (fails at base too).** `-10.50 a b` prints `Total: -$9.50`, because `parse_amount('-10.50')` returns `-950`. That's a separate bug in `parse_amount`'s sign handling. Fixing it means applying the sign to the whole amount, or rejecting negative input at the CLI if a negative bill makes no sense. The new `allocate` itself handles negative totals correctly (`-1000` over 3 gives `[-333, -333, -334]`).

## Principles that changed a decision

- **Fix root causes.** I fixed `allocate`, where the cent is lost. Printing the entered amount on the Total line instead would have hidden a share that is still short.
- **Test behavior.** The `allocate` test checks the sum and the spread rather than a fixed order. Only the receipt test, which shows what a user sees, pins who gets the extra cent.
- **Verifiable units.** The failing pin went in as its own commit, marked as expected failures, before the fix.
- **Prove it works.** My first run after the fix printed argparse "required: people" errors. zsh hadn't split the arguments, so the run was broken, not the code. I moved the proof into a bash script that reruns the same way and kept its output.
- **Smallest change.** The duplicate-name and negative-amount bugs have their own causes. They stay out of this change and are listed under Needs your call.
