Tasks can now have a due date. `python3 -m tasks add "Buy milk" --tag home --due 2026-11-01` stores it, and `list` prints `[ ] 1 Buy milk #home due 2026-11-01`. `list --overdue` shows only open tasks due before today, and prints `No tasks.` when there are none. A bad date such as `2026-02-30` exits with status 2, names the value on stderr, and stores nothing. Tasks without a due date print as before, and files written before this change still load. All of this is measured on the real CLI.

The repository has no remote, so there is no PR. The work is two commits on branch `feat/due-date`, with nothing uncommitted.

**The shape I chose**
- `Task.due` is an optional `datetime.date` (default `None`) in `tasks/model.py`.
- The date string is parsed in only two places, the `--due` flag and the file. Everything past those two points works with a real date or `None`.
- `Task.line()` adds ` due YYYY-MM-DD` after the tags. `Task.is_overdue(today)` holds the rule (open, has a due date, earlier than today). The CLI passes in `date.today()`, so the model never reads the clock.
- The file format lives only in `tasks/store.py`. A set date is stored as `"due": "YYYY-MM-DD"`. With no due date the key is left out, so a file that never uses due dates keeps today's shape. A missing key or `null` loads as no due date.
- `--due` is checked when the arguments are parsed, so a bad value exits 2 before anything is loaded or saved.

- Fixed (warning): what counted as `YYYY-MM-DD` depended on the Python version. On 3.11 and later, `date.fromisoformat` also accepts `20261101` and `2026-W44-1`. `--due` now accepts a value only if it reads back exactly as `YYYY-MM-DD`. I added `20261101` to the bad-date test. **Needs your call**
- The previous version cannot read a file once any task in it has a due date. It still reads files with none.
- `list --overdue --all` still shows only open tasks, because the request says "only the open tasks". `--overdue --tag T` applies both filters.
- A task due today is not overdue. "Today" is the machine's local date.
- A bad date prints argparse's usage line, then `tasks add: error: argument --due: invalid date value: '2026-02-30' (expected YYYY-MM-DD)`. stdout stays empty and the exit code is 2, the same form as the existing `done abc` error.
- Only zero-padded `YYYY-MM-DD` is accepted. `2026-1-1` is rejected.
- A broken stored date such as `"soon"` makes every command fail with a traceback. Malformed JSON already fails the same way.
- `list` does not mark overdue tasks. That was not asked for.

**Principles that changed a decision**
- Boundaries. The date is parsed once at the flag and once at the file, not inside `list`.
- Model the domain. `due` is a typed date and not a string, and the overdue rule sits on `Task` next to the field it reads.
- Design it as if it was always there. `today` is passed in, not read inside the model.
- Encode lessons in structure. A test, not a comment, guards the no-`due`-key file shape.
- Comments say why. The one new comment gives the Python 3.11+ reason for the exact-match check.
- Experience first. The error says the expected format, and `--due` shows `YYYY-MM-DD` in help.
- Test behavior. The tests assert CLI output, exit codes and the saved file, never internals.
