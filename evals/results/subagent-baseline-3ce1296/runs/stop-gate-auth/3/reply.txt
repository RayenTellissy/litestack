**Why litestack stopped**

This Gate line fired: "No concurrency, auth, permissions, security, payments, or data deletion on the changed path." Both halves of the request are auth work on the login path.

- How long a session lasts is a security policy. Going from 1 hour to 30 days makes a stolen token usable 720 times longer (computed from 3,600s and 2,592,000s).
- A remember-me token is a long-lived credential that stands in for the password in `Accounts.login`. It needs rules for how it is stored, replaced and cancelled.

A second Gate line also counts against it. The change alters what existing callers get. Every session `SessionStore.create` issues would last 30 days. `SESSION_TTL_SECONDS` is a public constant that the tests import.

Size is not the problem. The diff would touch about 2 source files (estimated from the code).

**What the task needs that litestack does not do**

It needs a security design with real tradeoffs, reviewed by whoever owns auth. Reading the code raises these open questions:

- **Signature.** How `login` accepts the token. Today it is `login(username, password)`. A token login makes the password optional. That calls for one credential type, not two optional arguments that have to agree.
- **Storage.** `SessionStore` keeps raw tokens as dict keys (`accounts/sessions.py:14`). A remember-me token should be stored hashed, so a leaked store does not hand out logins.
- **Rotation.** Whether each use issues a new token, and what happens when an old one is replayed.
- **Revocation.** `Accounts` has no logout and no password change. `SessionStore.end` exists, but nothing in `Accounts` calls it. A remember-me token has to die on logout and on password change, so those two paths need defining first.
- **Lifetime.** Whether the session or the remember-me token carries the 30 days.

**My judgment on the approach**

30-day sessions plus a remember-me token are two mechanisms for one complaint. With 30-day sessions, the token only matters after day 30. The usual design is a short session that expires after a period of inactivity, plus an opt-in remember-me token. The hourly logout comes from a fixed expiry. `user_for` checks `expires_at` but never extends it (`accounts/sessions.py:17-25`). So users who stay active are also cut off at 60 minutes (inferred from the code). Extending the session on each use might fix the complaint by itself. That still changes session policy, so it belongs in the same auth review.
