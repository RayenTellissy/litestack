**What you can do now**
- `python3 -m tasks add "Buy milk" --tag home --due 2026-11-01` saves the date with the task.
- `list` shows it after the title and tags, as in `[ ] 1 Buy milk #home due 2026-11-01`. Tasks without a date print exactly as before.
- `list --overdue` shows only open tasks whose date is before today. When there are none it prints `No tasks.` and exits 0.
- A bad date such as `2026-02-30` exits with status 2. It prints this to stderr, after argparse's usage line: `tasks add: error: argument --due: invalid date '2026-02-30', expected YYYY-MM-DD`. Nothing is saved (measured with `cmp` against a copy of the file).
- Old task files still load. I wrote a file by hand with no `due` key, and the reviewer used one written by the old code. Both list correctly, and new tasks can be added to them.

**How it's built**
- Each task gets an optional due date, stored as a real date inside the program and never as text.
- The date is checked once where it comes in. That happens at the `--due` option and again when the file is read. The rest of the code can trust it.
- The rule for "overdue" lives in one place, `Task.overdue(today)`, and it includes "not done". So adding `--all` can never bring done tasks into the overdue list.
- In the file the date is a `YYYY-MM-DD` string. Tasks without a date are saved without the key, so a file with no due dates looks exactly as it did before.

**Principles that changed a decision**
- **Boundaries:** dates are checked at the option and at the file read, not inside `cmd_add`.
- **Types and Model the domain:** `due` is a date, not text, and the overdue rule including "open" sits on `Task`, with no special case in `list`.
