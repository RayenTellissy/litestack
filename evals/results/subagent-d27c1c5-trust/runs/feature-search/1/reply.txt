Every request item now works. `python3 -m tasks search <text>` lists the open tasks whose title contains the text, ignoring case. It uses the same line format as `list`. `--all` adds done tasks, and a search with no match prints `No matching tasks.` and exits 1.

**What you can do now**
Anyone using the CLI can find tasks by part of their title instead of reading the whole list. Some examples from a run against a throwaway task file, after these commands:
- `add "Buy milk" --tag home`, `add "File taxes"`, `add "Milkshake recipe" --tag treat`, `add "STRASSE fegen"`, `done 1`

| Command | What it printed | Exit status |
|---|---|---|
| `search MILK` | `[ ] 3 Milkshake recipe #treat` | 0 |
| `search milk --all` | `[x] 1 Buy milk #home` and `[ ] 3 Milkshake recipe #treat` | 0 |
| `search --all milk` | the same two lines | 0 |
| `search eggs` | `No matching tasks.` | 1 |
| `search milk` before any task existed | `No matching tasks.` | 1 |
| `search straße` | `[ ] 4 STRASSE fegen` | 0 |
| `search` with no text | the usual argparse usage error | 2 |

Whoever maintains this next gets one new function, `cmd_search`, next to `cmd_list` in `tasks/cli.py`, plus its parser entry. Both commands print each task with `Task.line()`, so the output format still lives in one place. The README also has one new example line.

**The shape I chose and why**
- It adds no new type. The command takes a text string and an `--all` flag, filters the loaded tasks, and prints them.
- I skipped the separate design step. There is no new type, module, or signature that another module calls. `cmd_list` served as the model and I copied its structure.
- Case matching uses `casefold()`, Python's standard way to compare text without case. That is why `straße` matches `STRASSE` (measured, in the table above).

**Open decisions**
- **Where the no-match message goes.** It prints to normal output (stdout), the same way `list` prints its "No tasks." message. The other exit-1 message in the tool, `done`'s "No task 9.", goes to the error stream (stderr). This shows when output is piped: `tasks search x | wc -l` counts 1 line on a miss. Switching to stderr is a one-line change plus one line in the test.
- **No `--tag` on `search`.** The request names only `--all`, so I did not add tag filtering.
- **An empty search lists everything.** `search ""` lists every open task, because an empty string is part of every title.

**Principles that changed a decision**
- **Smallest change.** I left `--tag` off `search` and did not pull the shared "open unless `--all`" filter into a helper. It is one expression in one file.
- **Matching what the request names.** The request says to match `list`, so the no-match message follows `list`'s empty state and goes to stdout.
- **Test behavior.** The tests run the real CLI as a subprocess and check its output and exit status, not internal calls.
- **Verifiable units.** The failing tests went in as their own commit before the feature, so the history shows them failing and then passing.
- **Experience first.** I used `casefold()` rather than `lower()` so "ignoring case" also holds for text like ß.
